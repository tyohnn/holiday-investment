# 리서치 데이터 설계 원칙 — 파일 이름과 사실 시계열

> 2026-07-24 논의에서 확정한 설계 배경 문서. 구현 스펙은 플러그인 쪽이 정본이다:
> [data-layout.md](../plugin/skills/company-analysis/references/data-layout.md) ·
> [tracking.md](../plugin/skills/company-analysis/references/tracking.md).
> 이 문서는 "왜 이렇게 설계했는가"를 남긴다.

## 1. 파일 이름 — 수집일이 아니라 내용이 덮는 기간으로

### 핵심 관찰: DART 데이터는 불변 기록이다

FY2025 재무제표는 언제 받아도 같고, 2026-05-15 접수 공시도 영원히 같다.
그러니 **수집일은 파일명이 아니라 frontmatter에 있어야 할 정보**다.

수집일을 파일명에 쓰면(`2026-07-24-재무추이.md`) 두 가지가 깨진다:

- 내일 다시 수집하면 내용이 같아도 새 파일이 생겨 중복이 쌓인다.
- 정작 중요한 정보 — 이 데이터가 **언제부터 언제까지를 덮는지** — 는 어디에도 없다.

### 이름 규칙: 자료 성격에 따라 세 갈래

| 성격 | 예 | 이름 규칙 |
|---|---|---|
| **확정 기간 데이터** (한 번 확정되면 불변) | FY2025 재무제표, 사업보고서 | `재무제표-2025.md`, `사업보고서-2025.12-<접수번호>/` |
| **누적 시계열** (계속 확장) | 재무추이, 공시목록, 지분거래 | 날짜 없이 `재무추이.md` — 갱신하며 frontmatter에 `커버기간` |
| **수집 시점이 본질** | 뉴스 | `뉴스/2026-07.md` (월 버킷) — "그때 뭐가 보도됐나"가 정보 |

파생 규칙 둘:

- 유튜브 등 콘텐츠 자체에 시점이 있는 자료는 **콘텐츠의 날짜**(영상 업로드일)로 짓는다.
- **분석 리포트만은 날짜를 유지**한다(`분석/2026-07-24-심층분석.md`) — 분석은 특정 시점의
  판단이라 날짜가 곧 정체성이다. 요약하면: **raw는 내용 기간으로, 판단은 날짜로.**

### 재수집 시 숫자가 바뀌면 — 기재정정 감지

확정 기간 데이터가 바뀌는 경우는 사실상 **기재정정**뿐이고, 그건 그 자체로 중요한
신호다(회계 오류 수정이면 경계 대상). 그래서 이전본을 쌓아두는 대신 **덮어쓰되 변경을
감지해서 알린다** — API 응답의 접수번호(rcept_no)를 manifest.json에 사업연도별로 기록해
두면, 재수집 때 번호가 달라진 연도가 곧 정정된 연도다. 값 비교 없이 정확히 특정된다.
"FY2024가 정정됐다"는 사실 자체는 트래킹 문서의 한 줄이 된다.

## 2. 사실 시계열(트래킹) 문서 — 종단면을 만든다

### 왜 필요한가

사업보고서는 **횡단면 스냅샷**인데, 투자 판단에 필요한 건 **종단면 변화**다.
매년 보고서를 따로 읽으면 "작년 대비 뭐가 달라졌나"가 안 보인다. 여러 자료(사업보고서
주석·공시·IR·뉴스)에서 한 주제의 사실만 뽑아 시간순으로 쌓는 문서가 그 간극을 메운다.

계층상 위치: `자료`(raw) → **`트래킹`(정제된 사실)** → `계산` → `분석`(판단).

### 형태 — DB 사실 원장이 정본, md는 생성된 뷰 (A2 판정, 2026-07-25)

> **판정 완료.** 정본은 `trackings` 테이블(append-only 원장)이고, `리서치/기업/<종목>/트래킹/*.md`
> 는 `tracking.py export-md` 가 만드는 **생성물**이다 — 직접 편집하지 않는다. 사실 추가는
> `tracking.py add` 를 거친다. 근거는 아래 "A2 실험 결과", 원칙(시간순·추가만·출처 필수·
> 해석 금지)은 저장 형태와 무관하게 그대로다.

```markdown
---
주제: 전환사채 잔액과 전환청구
최초작성: 2026-07-24
최종갱신: 2026-07-24
---

| 시점 | 사실 | 수치 | 출처 |
|---|---|---|---|
| 2024-03-15 | CB 발행 (전환가 24,000원, 만기 2029) | 1,500억 | 주요사항보고서 |
| 2025-12-31 | 300억 전환청구, 잔액 감소 | 잔액 1,200억 | 사업보고서 2025.12 주석 15 |
| 2026-05-20 | 잔액 확인 | 900억 | 분기보고서 2026.1Q |
```

### 설계 원칙

- **오래된 것 → 최신 순** — 읽으면 변화가 이야기로 읽힌다.
- **줄은 추가만, 수정 금지** — 사실은 불변이다. 정정되면 "정정됐다"는 사실을 새 줄로 추가한다.
- **출처 필수** — 어느 보고서 어느 주석에서 나왔는지. 접수번호가 있으면 함께.
- **해석 금지** — 사실만 담는다. 판단("따라서 저평가다")은 분석 리포트에서.
- **수치는 별도 열** — 나중에 대시보드가 그래프로 그릴 수 있고, 스캔이 쉽다.
- **주제는 자유 생성하되 기본 세트를 제시** — 채무·자금조달 / 지분·지배구조 /
  캐파·투자 집행 / 수주·계약 / 제품 파이프라인 / 소송·규제·우발부채 / 이익률 구조 /
  경영진·핵심 인재. 해당 사항 있는 주제만 만들고, 업종에 맞게 번역한다
  (게임사: 캐파→제작 파이프라인·M&A, 수주→퍼블리싱 계약·판호).

### A2 실험 결과 — 왜 원장인가 (2026-07-25)

같은 갱신 과제(신규 적재된 공시 5건 + 증권신고서를 트래킹에 반영)를 두 서브에이전트에게
각각 md 편집 / CLI 원장 입력으로 시키고, 로드맵의 판정 기준 5개로 비교했다.

| 기준 | A안 (md 직접 편집) | B안 (DB 원장 + CLI) |
|---|---|---|
| ① 에이전트 마찰 | 도구 호출 ~20회, 편집 9회. **시간순 삽입이 최대 마찰** — 신규 5건 중 4건이 기존 최초 행보다 과거라 표 중간에 두 번 나눠 삽입, 같은 날짜 행의 상대 순서는 임의 결정 | 도구 호출 ~9회, CLI 4회. 입력 순서 무관(조회 시 정렬) — "md였다면 어느 줄 사이에 끼울지 직접 찾아야 했을 것" |
| ② 중복 처리 | **전적으로 수동(육안)**. 에이전트 자백: "접수번호로 검색했어야 더 안전했는데 육안 확인만 했다 — 놓칠 위험이 실제로 있었다" | 자동 감지. 단 "안전망일 뿐 사전 확인 비용은 줄지 않음"(어느 주제에 넣을지 판단하려면 기존 원장을 읽어야 함) |
| ③ UI 렌더 | md 파싱 계층을 UI가 떠안음 | PostgREST로 JSON 즉시 |
| ④ 크로스 종목 쿼리 | 전 종목 폴더 glob + 정규식 파서 (2,700종목이면 전량 순회) | SQL 1회 |
| ⑤ 정정 표현 | 에이전트가 매번 손으로 옮겨 적음 | **정형 데이터에서 SQL로 자동 생성** (LLM 비용 0) |
| 소요 | 110,774 토큰 · 5.2분 | 102,065 토큰 · 3.6분 |

결정적이었던 것은 마찰 총량보다 **md의 조용한 실패**다.

- **데이터 소실**: md 트래킹을 파싱하니 1행이 사라졌다. 원인은 날짜 `2025-09`(월만 아는
  사실) — 에이전트가 자연스럽게 쓴 표기인데 `YYYY-MM-DD` 파서에 안 걸렸다. md는 조용히
  통과시키고 **읽을 때** 잃는다. 원장은 입력 시점에 거부한다(fail fast).
- **문서 내 자기모순**: A안 에이전트가 IPO 사실을 추가하다 기존 서문("유상증자·CB 발행
  이력은 확인되지 않는다")과 모순됨을 뒤늦게 발견했다. "놓쳤으면 자기모순 문장이 남을
  뻔했다"고 보고. 원장은 서술 문맥이 없어 이 실패 자체가 불가능하다.
- **같은 사실의 이중 기록**: 두 에이전트가 같은 공시(20170814001313)를 각각 접수일
  2017-08-14 / 합병기일 2017-09-01로 기록했다. 문장·날짜 기반 중복 키로는 못 잡는다
  → 중복 키를 `(주제, 접수번호)` 1순위로 바꿨다.

md의 강점으로 남는 것은 "파일시스템 grep과 diff로 훑는 익숙함"인데, 이는 **생성된 md 뷰**로
그대로 유지된다 — 정본만 원장으로 옮기면 잃는 것이 없다.

### 실험에서 도출된 스키마 개선

1. **`date_precision`** (day/month/quarter/year) — 사실의 시점 정밀도는 데이터의 성질이다.
   에이전트는 `2025-09`·`2022`·`2026 1Q`를 자연스럽게 쓰며, CLI가 이를 정규화해 저장하고
   md 뷰에서 원래 표기로 복원한다.
2. **`tags`** (배열) — "IPO 자금사용목적: 타법인증권취득"은 자금조달이면서 M&A다. A안
   에이전트가 "어느 문서에 넣을지 임의 판단했고 확신 못 한다"고 보고 → 주제는 단일 분류가
   아니라 primary topic + 태그. (로드맵 열린 질문 "분류 vs 태그"의 답)
3. **`fact_date` 기준 명문화** — 공시발 사실은 **접수일** 기준. 이사회결의일·효력발생일은
   본문/수치에 적는다. (기준이 없어 두 에이전트가 다른 날짜를 쓴 사례에서 도출)

### 방법론과의 연결

- **A4 "매수 이유 스토리를 적어 추적하라"** — 스토리의 유지/훼손을 판정할 사실 근거가 여기 쌓인다
  (판정 자체는 판단이므로 분석 리포트에 남긴다).
- **B4 피셔 "예측이 아니라 팩트(수주·제품·공장) 추적"** — 매수 타이밍 3단계 판정의 근거.
- **"회사별 사풍(부풀리는 회사 vs 보수적 회사)을 보정해 읽어라"** — 발표한 계획과 실제
  이행이 시간축으로 나란히 쌓이면, 감으로 하던 사풍 판정에 증거가 생긴다. 다음 가이던스를
  얼마나 할인해 읽을지가 데이터로 결정된다. 이 문서의 가장 큰 실전 효과다.
