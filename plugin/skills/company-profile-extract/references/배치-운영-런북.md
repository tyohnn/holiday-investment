2026-08-26 상장 368개사 실행에서 확정된 절차. 서브에이전트에게 줄 지시서는
`배치-서브에이전트-프롬프트.md` 이고, 이 문서는 **감독** 쪽 절차다.

## 새 세션에서 시작하는 법

사용자가 이렇게만 말하면 된다:

> `plugin/skills/company-profile-extract/references/배치-운영-런북.md` 대로
> 아직 안 된 회사 배치로 돌려줘.

스킬(`SKILL.md`)만 지목하면 **부족하다** — 스킬은 회사 1건 처리 절차이고, 배치
오케스트레이션과 실행 중 배운 운영 규칙은 이 두 문서에만 있다.

## 1. 대상 회사 목록 만들기

**"원문(zip)이 이미 있는 회사"만** 대상이다. Phase 3(공시 수집)가 아직 안 받은 회사는
어차피 `확인불가:Storage에원문없음` 으로 실패한다.

```bash
# filing_docs 에서 사업보고서 원문 보유 회사를 페이지네이션으로 수집
# ★ order 를 반드시 넣는다 — PostgREST 는 정렬 없이는 불안정한 페이지를 준다(실측 함정)
offset=0
> /tmp/corps.txt
while [ $offset -le 40000 ]; do
  resp=$(curl -s -G "$SUPABASE_REST_URL/filing_docs" \
    --data-urlencode "select=rcept_no,filings!inner(corp_code,report_nm)" \
    --data-urlencode "status=eq.ok" \
    --data-urlencode "filings.report_nm=ilike.*사업보고서*" \
    --data-urlencode "order=rcept_no" \
    --data-urlencode "limit=1000" --data-urlencode "offset=$offset" \
    -H "apikey: $SUPABASE_SERVICE_KEY" -H "Authorization: Bearer $SUPABASE_SERVICE_KEY")
  n=$(echo "$resp" | python3 -c "
import sys,json
d=json.load(sys.stdin)
with open('/tmp/corps.txt','a') as f:
    for r in d:
        fl=r.get('filings');  fl=fl[0] if isinstance(fl,list) and fl else fl
        if isinstance(fl,dict) and fl.get('corp_code'): f.write(fl['corp_code']+chr(10))
print(len(d))")
  offset=$((offset+1000)); [ "$n" -lt 1000 ] && break
done
sort -u /tmp/corps.txt -o /tmp/corps.txt; wc -l < /tmp/corps.txt
```

**이미 처리한 회사를 빼려면** `fin_details`/`corp_history` 에 행이 있는 회사를 제외한다
(`extract_profile.py pending` 도 있으나, "처리했는데 0행" 과 "미처리" 를 구분하지 못하는
알려진 공백이 있다).

5개면 감독 취합 오버헤드가 커진다.

## 3. 서브에이전트 기동

- **모델은 sonnet.** 감독(메인)이 Opus 로 검증한다 — `AGENTS.md` 역할 분담.
- **웨이브로 나눠 띄운다.** 한 번에 8~15개. 37개를 한꺼번에 띄우면 DB 부하가 몰린다
  (실측: PostgREST statement timeout 으로 워커가 죽었다).
- 각 프롬프트는 **짧게** — 공통 지시서 파일을 읽히고 배치 고유값만 준다:

> 먼저 `plugin/skills/company-profile-extract/references/배치-서브에이전트-프롬프트.md`
> 를 Read 로 읽어라. 그 파일이 네 작업 지시서 전문이다. 아래는 이 배치 고유값이다.
> - 배치 번호: **NN**
> - 대상 10개사: `00100601,00100939,...`
> - 폴백 out-dir: `/tmp/fallback/batchNN`
> - 상세 보고서 경로: `/tmp/reports/batchNN.md`

## 4. 감독의 QC (생략하지 않는다)

서브에이전트가 스스로 적은 단서가 곧 결함 신호다. 실측으로 확인된 것:

- **"코드 결함 발견, 보고만 함"** → 재현 → 수정 → **삼성 회귀** → 그때만 반영.
  ```bash
  python3 plugin/skills/company-profile-extract/scripts/extract_profile.py verify \
      --corps 00126380 --rcepts 20260310002820,20250311001085
  ```
  블록별 적재/확인불가/게이트보류 수치가 이전과 같아야 한다.
- **에이전트 진단이 틀릴 수 있다.** "크래시" 라고 보고된 것이 실제로는 조용한 데이터
  오염이었던 사례가 있다(연혁 19xx). 직접 재현해서 확인한다.
- **DB 로 대조한다.** 보고된 적재 행수가 실제로 들어갔는지 조회한다.
- **불가능한 값을 찾는다.** R&D > 매출, 미래 연도 period_key, 합계 100% 인 시장점유율.
  이 셋이 실제로 대형 결함 3건을 잡아냈다.

## 5. ★ 재적재할 때 절대 하지 말 것

**`extract` 를 그냥 재실행하면 안 된다.** `load_scope()` 가 ALL_CONCEPTS 전체에
`replace_scope` 를 걸어, 규칙이 0행으로 내는 블록(연혁·부문별매출·시장점유율)의
**에이전트 산출물이 통째로 지워진다**(2026-08-26 실측: fin_details -2,819 ·
corp_history -3,512 행).

특정 개념만 고칠 때는 반드시:
```bash
python3 .../extract_profile.py extract --corps <목록> --concepts rnd_total,rnd_revenue_ratio
```
`--concepts` 를 주면 그 개념만 교체하고 나머지 개념과 `corp_history` 는 건드리지 않는다.

**복구 재료를 지우지 마라.** 에이전트가 만든 `/tmp/fallback/*/*.ingest.json` 이 유일한
복구 수단이다. 위 사고에서 이 파일들로 160/161 개사를 되살렸다:
```bash
python3 .../llm_fallback.py ingest --json <파일>
```
