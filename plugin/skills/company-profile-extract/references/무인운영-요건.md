# 무인 운영 요건 — `company-profile-extract` 파서를 고치며 실제로 마주친 것

2026-08-25. `extract_profile.py`의 크래시(A)·앵커(B)·열 인덱스(C) 결함을 고치는 동안 코드를
직접 읽고 만지면서 발견한 것만 적는다. 추측·일반론은 "확인 불가"로 표시했다.

## 1. 실패를 어디에 남겨야 다음날 이어서 처리할 수 있나 — **지금은 그 자리가 없다**

`run()`은 이제(오늘 수정) 회사·회차 단위로 예외를 잡아 콘솔에 traceback을 찍고 `failures`
리스트를 모아 종료 코드(1)로 신호한다. 하지만 이건 **그 프로세스가 살아있는 동안의 메모리
안**에만 있다 — 콘솔 로그가 스크롤되거나 cron 로그가 로테이션되면 "어제 무엇이 실패했는지"를
아는 방법이 없다.

**같은 요구를 위한 인프라가 이 레포에 이미 있다** — 그러나 이 스킬엔 안 맞는다:
`platform/ingest/backfill.py` + `ingest_progress` 테이블(`platform/supabase/migrations/
20260802000002_ingest_progress.sql`)이 정확히 "회사 순회 중 실패한 것을 기록해 다음날
이어서 처리"를 이미 구현했다(`mark_running`/`mark_done`/`mark_pending`/`mark_failed`/
`mark_skipped`, `pending→running→done|failed` 상태기계, 재시작 시 done은 API 콜 없이
건너뜀). 다만:
- `ingest_progress.stage`에 **CHECK 제약이 걸려 있다**: `('company','filings','fin','items',
  'events','regs','ownership','docs')` 8개 고정값뿐이다. `'profile_extract'` 같은 새 stage를
  넣으려면 **마이그레이션으로 제약을 바꿔야 한다** — 코드만 고쳐서는 못 넣는다.
- **grain이 (corp_code, stage)뿐이다** (PRIMARY KEY). 이 스킬이 실패한 단위는 (corp_code,
  **rcept_no**)다 — 한 회사가 사업보고서를 여러 건(연차별) 가질 수 있는데 이 테이블엔
  rcept_no 컬럼 자체가 없다. 그대로 재사용하면 같은 회사의 다른 rcept 실패를 구분 못 한다.

**결론(확인 불가 아님, 코드로 확인함)**: 재사용하려면 ①`ingest_progress`에 새 stage를 추가
하는 마이그레이션 + rcept_no 컬럼 추가(또는 별도 테이블), 아니면 ②이 스킬 전용의 작은
(corp_code, rcept_no, status, last_error, attempts, updated_at) 테이블을 새로 만드는 것,
둘 중 하나가 필요하다. 지금은 아무것도 없다 — 오늘 추가한 `run()`의 실패 목록은 "그 프로세스가
끝나기 직전에 사람이 콘솔을 보면 안다" 수준이지 "다음날 자동으로 그 목록만 골라 재실행한다"
수준이 아니다.

## 2. "재시도하면 되는 것" vs "사람이 봐야 하는 것" — 오늘 실측으로 경계가 뚜렷해졌다

`platform/ingest/ingest.py`의 `rest()`/`storage_download()`는 이미 네트워크성 실패(URLError,
5xx, 429, timeout, DNS 실패)에 10회·최대 300초 백오프 재시도를 갖고 있다(재사용됨). 즉 이
스킬의 REST/Storage 호출이 겪는 "재시도하면 풀리는" 실패는 이미 아래에서 흡수되고, 위로
올라오는 예외는 재시도를 **다 쓰고도** 실패한 것(`RuntimeError`)뿐이다.

오늘 고친 크래시(`parse_treasury`의 `TypeError`)는 이것과 **완전히 다른 종류**였다 —
네트워크와 무관한 **순수 로직 버그**로, 몇 번을 재시도해도 100% 같은 입력에 100% 같은 예외가
난다(deterministic). 이번에 마주친 예외를 분류하면:

| 종류 | 예 | 재시도 효과 |
|---|---|---|
| 네트워크/인프라 일시 장애 | DNS 실패, 5xx, 429, timeout | 이미 `ingest.rest()`가 흡수. 위로 올라오면 재시도를 다 쓴 것 — 다음날 재시도하면 풀릴 수도 있다 |
| 파싱 로직 버그 | `parse_treasury`의 `TypeError`(오늘 고침) | 재시도 무의미. 코드를 고치기 전까진 몇 번을 돌려도 같은 회사·회차에서 똑같이 죽는다 — **사람이 봐야 한다** |
| 스키마 전제 불일치 | `issued`/`treasury` 열 인덱스가 회사마다 다름(오늘 고침) | 위와 같음 — 조용히 틀린 숫자를 낼 수도 있어(크래시조차 안 나는 경우) 더 위험하다 |

`run()`의 새 try/except는 **이 둘을 구분하지 않고** 뭉뚱그려 잡는다(`except Exception`).
무인화 다음 단계에서 필요한 것: 예외 타입/메시지로 이 둘을 나눠, 전자는 "내일 자동 재시도
대상"으로 큐에 남기고 후자는 "사람에게 알림 + 그 (corp_code, rcept_no)를 스킵 목록에 넣어
무한 재시도(같은 버그에 매일 부딪히는 것)를 막는" 분기가 필요하다. 지금은 이 분기가 없다 —
`exc_type`만 기록해 사람이 매번 읽고 판단해야 한다.

## 3. 신규 공시를 어떻게 감지하나 — **이 스크립트의 책임이 아니다(설계상 맞다), 그런데 그걸 잇는 코드가 없다**

`extract_profile.py`는 **DART API를 호출하지 않는다**(Storage와 PostgREST만 읽는다) —
이건 의도된 설계이고 맞는 경계다: "오늘 새 공시가 떴는지" 감지하고 원문을 Storage에 내려받는
건 `backfill.py`(Phase 3, DART API 호출)의 몫이고, 이 스킬은 그 결과물(`docs/<corp_code>/
<rcept_no>.sections.json.gz`)이 이미 있다고 가정하는 순수 다운스트림 소비자다. 역할 분리
자체는 건드릴 필요가 없다.

다만 "이 스킬이 아직 처리 안 한 rcept_no를 어떻게 고르나"는 **코드에 없다**. 지금 CLI는
① `--rcepts`를 명시하거나 ② 회사별 **최신 사업보고서 1건**(`latest_annual_rcept`)만 자동
선택한다 — "filings에는 있는데 fin_details/corp_history에 아직 안 실린 rcept 전체"를
찾는 쿼리나 명령이 없다(`grep`으로 확인, 그런 로직 자체가 없다). 무인화하려면 최소한
"이 corp_code의 사업보고서 rcept_no 중 `source_rcept_no`로 `fin_details`에 한 번도 안 나온
것"을 매일 diff하는 단계가 필요한데, PostgREST의 `not.in` 필터로는 대상 집합이 크면(수천
rcept) 부담스러울 수 있어 정확한 방식은 미확인(확인 불가 — 이번 범위에서 설계 안 함).

## 4. 같은 보고서를 두 번 처리하지 않으려면 — **정확성 관점에선 이미 멱등하다(실측), 비용 관점에선 스킵 로직이 없다**

`load_scope()`가 (`corp_code` × `concept` × `source_rcept_no`) 단위로 **delete→insert**
(replace_scope, `on_conflict`까지 걸려 merge-duplicates)를 쓴다 — 같은 rcept를 몇 번 다시
돌려도 최종 상태는 같다. 오늘 이걸 직접 검증했다: 삼성전자 두 rcept를 재실행 전후로
`fin_details=237행`·`corp_history=45행` 그대로였고, 자사주 값(`33.41`/`33.4117` 등)도
동일했다. **정확성 문제는 없다.**

다만 이건 "다시 돌려도 안전하다"이지 "다시 돌 필요가 없다는 걸 안다"가 아니다 — 지금 스크립트는
같은 (corp_code, rcept_no)를 몇 번 넘겨도 **매번 Storage 다운로드 + 파싱 + REST 왕복을 그대로
반복**한다. 무인 배치가 매일 "이 회사 목록을 다시 훑어라" 식으로 돌면, 이미 처리된 rcept까지
매번 다시 받는 비용이 쌓인다. "이미 `fin_details`에 이 (corp_code, source_rcept_no) 조합이
있으면 스킵"하는 사전 필터가 없다 — 필요하면 추가해야 한다(확인 불가 — 오늘은 추가하지 않았다,
범위 밖).

## 5. LLM과 규칙 파서의 분업 경계 — 오늘 고친 것 자체가 그 경계의 실측 증거다

오늘 고친 세 결함(A 크래시, B 앵커, C 열 인덱스)은 **전부 "표는 있는데 회차·회사마다 위치가
살짝 다르다"는 문제였고, 전부 규칙(정규식 + 서브헤더에서 위치를 동적으로 찾기)만으로 풀렸다.**
구체적으로:
- B(기수→연도 앵커)는 언뜻 "문서를 읽고 이해해야 하는" 자유형 작업처럼 보였지만, 실제로는
  `filings.report_nm`(DB에 이미 있는 구조화된 값)을 표의 첫 컬럼에 대응시키는 **완전히
  규칙적인 대체 앵커**로 풀렸다. LLM 없이 정규식 하나로 세 회사 다 통과했다(실측: 삼양식품
  R&D 3행 정상 적재, `report_nm회계연도역산` 경로).
- C(열 인덱스)도 "우선주 유무로 열 수가 다르다"는 표 구조 문제였지만, 표 안의 서브헤더
  행(`보통주|우선주|합계|...`)에서 "합계"라는 **문자열을 찾는 것만으로** 해결됐다 — 이것도
  자유형 이해가 아니라 규칙이다.

**반면 스크래치패드 진단(재현성-시험-3사.md)이 이미 실측한 4개 블록(연혁·부문별매출·
시장점유율 중 상당수)은 오늘 안 고쳤고, 이유가 다르다**: 표의 **개념적 축 자체**가 회사마다
다르다(금융업은 업종×세부부문 2단 헤더로 매출이 아니라 "영업수익", 제조업은 부문>제품>품목
4단 계층, 건설업은 공사종류×국내/해외 축) — 이건 "위치를 찾는" 문제가 아니라 "이 표가
무엇을 말하는지 해석해야 하는" 문제라 회사별 화이트리스트(`SEGMENT_SUMMARY_WHITELIST`)를
끝없이 늘리는 것 말고는 규칙으로 일반화가 안 된다. 연혁도 마찬가지 — 헤더 라벨이 회사마다
다르고(`연도`/`일자`/`주요변동사항`), 표가 아예 없이 산문으로만 존재하는 회사(동신건설)도
있다.

**오늘 실측이 보여준 분업 기준**: "표 구조는 같은데 열/행 위치나 라벨 문자열이 회차마다
바뀐다" → 규칙(서브헤더·정규식으로 동적 탐색). "표의 축 자체가 회사·업종마다 다른 개념을
쓴다" 또는 "표가 아예 없다" → LLM(문서를 읽고 이 회사의 방식대로 재구성해야 함). 이 경계선은
겉으로 "표 구조가 회사마다 다르다"로 뭉뚱그려지기 쉽지만 난이도가 완전히 다르다 — 전자는
한 함수 안에서 끝나고(오늘 한 일), 후자는 회사마다 새 파서를 계속 추가해야 해서 규칙으로는
발산한다.

## 그 밖에 코드를 만지며 마주친 것

- **`run()`의 예외 격리는 (corp_code, rcept_no) 단위지, 5블록 단위가 아니다.** 한 rcept
  안에서 `parse_market_share` 같은 특정 블록 파서 하나가 새로 죽으면, 이미 성공했을 나머지
  4블록(R&D·연혁·주주현황 등)도 그 rcept 전체와 함께 버려진다. 오늘 요구받은 "회사·블록
  단위 격리"는 회사×회차(콘솔에 찍히는 `=== corp=%s rcept=%s ===` 단위) 수준까지 구현했고,
  블록(파서 함수) 단위 격리(`facts += parse_rd(...)` 각각을 개별 try/except로 감싸는 것)는
  범위 밖으로 남겼다 — 다음 단계 후보다.
- **`load_scope()`의 delete→insert는 concept별로 개별 요청이고 트랜잭션이 없다**(코드
  주석에 이미 명시됨). 한 rcept 처리 중 여러 concept를 순회하다 중간에 예외가 나면 일부
  concept만 갱신되고 나머지는 갱신 전 상태로 남는다 — 다만 재시도(같은 rcept 재실행)로
  결국 일관 상태가 된다(멱등성 자체는 유지). 동시에 두 프로세스가 같은 rcept를 건드리는
  것을 막는 락은 없다(cron이 겹쳐 도는 경우 등) — 확인 불가, 오늘 실측 범위 밖.
- **`report_fiscal_year(rcept_no)` 호출이 이제 매 rcept마다 무조건 1회 실행된다**(리팩터링
  전엔 조건부). REST 왕복 1회 추가 — 2,659개사 규모에서 무시할 수준인지, 배치 시작 시
  `filings`를 통째로 긁어 로컬 딕셔너리로 캐싱하는 게 나은지는 확인 안 함(범위 밖).
