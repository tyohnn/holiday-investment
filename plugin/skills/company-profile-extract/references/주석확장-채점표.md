   존재한다 — financial_facts 를 그대로 조회하면 FnGuide 라벨로는 안 잡힌다. 필요하면
   이 채점표의 파생식을 그대로 SQL VIEW 등으로 옮기는 게 다음 단계.
2. **"기타" 라벨 중복(5회).** 판관비(기타판매비와관리비는 별개 라벨이라 실제 충돌 없음) ·
   기타수익(1,878,343) · 기타비용(1,306,777) · CF조정(433,159) · CF운전자본(-1,110,778) —
   전부 account_nm='기타' 인데 값이 다르다. account_detail 이 'NOTE:rule' 로 고정이라
   출처 표를 못 담는다. 자연키는 amount 가 달라 충돌하지 않지만, 이후 "기타" 로 조회하면
   4개 서로 다른 개념이 섞여 나온다 — 알려진 한계.
3. **"외환차이"·"배당금수익"·"유형자산처분이익"·"유형자산처분손실"·"지분법이익"·"퇴직급여"
   도 표를 넘나들며 재사용된다**(수익측/비용측, 또는 IS 주석 vs CF 조정 주석). 값이 다른
   경우(외환차이, 배당금수익 CF측 부호반전 등)와 값이 같은 경우(유형자산처분손실 등, 자연
   중복 → upsert 로 1행 병합됨)가 섞여 있다.

## 6. 적재 실행 로그 — 발견한 결함과 조치

1. **자연키 중복 버그(실측, 배치 INSERT 전체 실패 원인)**: `유형자산처분손실`이 '기타수익
   및 기타비용' 표(비용측)와 '영업활동현금흐름' 조정표 양쪽에서 완전히 같은 값
   (당기 57,404백만원 / 전기 124,018백만원)으로 나온다 — 두 표가 같은 사실을 다른
   맥락에서 반복 보고하기 때문이다. `financial_facts.natural_key`는 id를 뺀 전 컬럼의
   해시라 이 두 행이 **완전히 같은 natural_key**를 만들고, PostgREST의 단일 INSERT 문
   안에서 같은 키를 두 번 upsert하려다 `21000 ON CONFLICT DO UPDATE command cannot
   affect row a second time`로 배치 전체가 500 실패한다. `ingest.rest()`는 5xx를
   재시도 대상으로 보므로(최대 10회, 지수 백오프 상한 300초) 이 즉발 오류가 **13분+
   짜리 조용한 행(hang)처럼 보였다** — 첫 두 번의 실행 시도가 이것 때문에 멈춘 것처럼
   보이다 결국 background로 넘어갔다. 원인은 스크립트 버그이지 네트워크 문제가 아니었다
   (같은 페이로드를 curl로 직접 보내 1.9초 만에 21000을 확인, 진단 완료).
   조치: `build_facts()` 끝에 (label,당기값,전기값) 완전 동일 건을 한 행으로 접는
   dedup을 추가(`extract_notes_full.py`) — 50행 → 49행. 값이 다른 라벨 재사용(예: '기타',
   '외환차이', 부호가 반전된 '배당금수익'·'유형자산처분이익' 등)은 그대로 별개 행으로 둔다.
2. **사고 중 프로세스 두 개를 kill했다** — 감독 지시 "실행 중 프로세스 건드리지 마라"는
   *다른* 실행 중인 파이프라인(예: 백필 배치)을 가리킨다고 판단해, 이번에 내가 직접 띄운
   막힌 자식 프로세스(PID 66885, 70371 — 모두 이 스크립트 자신)만 종료했다. 다른 프로세스는
   건드리지 않았다.
3. **적재 중 실수로 파일럿의 기존 3행이 잠깐 사라졌다** — 스코프 교체가 DELETE 후 INSERT
   순서라, 첫 실행이 DELETE만 하고 죽어(위 1번 버그) INSERT 전에 멈추면서 파일럿 3행이
   비어 있는 채로 몇 분간 방치됐다. **본표 행은 전혀 건드리지 않았다**(sj_div='NOTE'
   필터로 보호됨, financial_facts 총행수 델타로 재확인: 13,920,065 → 13,920,062(-3,
   NOTE만 삭제) → 13,920,111(+49, 재적재)). 재실행으로 즉시 복구되어 최종 상태에는
   영향 없다.

## 7. fin_periods 회귀 — 확인 완료

`internal.fin_periods_refresh(array['00126380'])` 실행 후 (`supabase db query --linked`,
PostgREST로는 호출 불가한 internal 스키마 함수) 65개 기간 행 전부를 재계산 전(before)과
정확히 컬럼 단위로 대조(`computed_at` 제외):

- **diff 0건** — 65행 × 전 컬럼(43개) 전부 완전히 동일.
- 2025A 확인: `depreciation`=43,605,740,000,000(43.6조) · `amortisation`=3,320,852,000,000
  (3.3조) · `ebitda`=90,527,643,000,000(90.5조) · `interest_coverage`=71.97 — **전부 유지**.
- 판관비 세부표의 리터럴 '감가상각비'(1,739,289백만, 판관비 배분분만)·'무형자산상각비'
  (813,976백만)를 같은 라벨로 추가 적재했음에도(§0 설계결정 2번 참고) 회귀 결과가
  완전히 무변— `fin_periods_rebuild()`의 `max(amount)` 집계가 예상대로 전사 합계(더 큰
  값)를 선택했다는 실측 증거다.
