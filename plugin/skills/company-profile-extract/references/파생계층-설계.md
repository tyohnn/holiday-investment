# 파생 지표 계층 설계 — `fin_periods` 확장 전략

2026-08-09 논의 정리. 실측 근거는 원격 Supabase(`kglymnsytrenlbodmbid`) 기준.

## 배경

`financial_facts`(원본 13,920,062행)는 Storage로 이관했고, 웹앱은 `fin_periods`(파생
134,279행)만 읽는다. 원본을 DB에 두고 스크리너를 돌리면 9,598 ms, 파생으로는 9.9 ms —
966배 차이가 이 계층의 존재 이유다.

분기 기준은 **"회사를 가로지르는가"**다. 자주 쓰는지가 아니다.

- **가로지름**(스크리너·순위표·섹터 비교) → 반드시 Postgres. Storage로는 2,659개 객체를
  다 열어야 해서 불가능하다.
- **한 회사만**(상세 화면) → Storage로 충분. 왕복 90 ms.

## 1. 자주 쓰이는 계정을 컬럼으로 추가한다

### 결정
웹 화면이 바로 테이블로 그리는 계정은 `fin_periods`에 컬럼으로 편다.

### 당장 추가 대상 (FnGuide 재무비율 표 기준)
| 컬럼 | 쓰이는 곳 |
|---|---|
| 유동자산 | 유동비율 |
| 유동부채 | 유동비율·당좌비율 |
| 당좌자산 | 당좌비율 |
| 자본금 | 유보율 |
| 유보액 | 유보율 |
| 이자비용 | 이자보상배율 |

이 6개를 더하면 안정성비율 8개가 전부 그려진다. 현재는 3개(부채비율·자기자본비율·
순부채비율)만 가능.

### 한계 — 컬럼으로 다 펼 수는 없다
실측: 고유 `account_id` 1,002개, 분포는 롱테일이다.

```
상위  50개 → 37.0%
상위 100개 → 51.8%
상위 200개 → 69.1%
상위 300개 → 80.8%
```

전부 컬럼화하면 1,000열 대부분 NULL인 테이블이 된다. **상위 50개 언저리가 이 층의
자연스러운 한계**이고, 나머지는 4번의 long 테이블로 간다.

### ★ 선행 조건 — 정의를 먼저 확정한다
컬럼을 늘리기 전에 **정의를 문서화**해야 한다. 이미 실제 불일치가 나왔다.

- **`net_debt`**: 삼성 2022 기준 우리 -39조, FnGuide -105조. FnGuide는 단기금융상품까지
  현금성으로 잡는 것으로 보인다. 어느 쪽이 틀린 게 아니라 **선택**인데, 우리 선택이
  문서화돼 있지 않다.
- **`debt_ratio_pct`**: 소수 1자리로 저장돼 26.4063이 26.40이 된다. FnGuide는 26.41.
  화면에서 2자리를 쓰려면 저장 정밀도를 올리거나 원자재(`liabilities`/`equity`)로
  화면에서 계산해야 한다.

각 컬럼에 **계산식·단위·연결/별도 기준·출처 sj_div**를 컬럼 코멘트로 남긴다.

## 2. 채움률이 낮은 컬럼 — 원인이 셋이고, 처방이 다르다

### ★ 논의 중 정정된 부분
"채움률이 낮은 건 계정 표준화가 안 돼서"라는 전제는 **컬럼마다 다르다.** 원인을 세
갈래로 나누지 않으면 잘못된 처방을 하게 된다.

### (a) 원천에 데이터가 없음 — LLM으로 못 채운다
`depreciation` 19.3% · `amortisation` 17.6% · `ebitda` 19.2%

마이그레이션 `20260806000001` 주석에 이미 조사돼 있다:

> 감가상각비 33.7%는 매칭 실패가 아니라 원천의 성질이다. 가장 넓은 그물
> (`account_nm like '%감가상각%'` and not like `'%누계액%'`)로 세어도 911사뿐이다.
> 즉 `finstate_all`에 감가상각 라인을 아예 싣지 않는 회사가 3분의 2다.

**계정명이 깨진 게 아니라 응답에 그 줄이 없다.** LLM에게 채우게 하면 없는 숫자를
만들어내는 것이 된다. 이건 **주석(Phase 3)에서 가져와야 하는 항목**이고, 4번의 영역이다.

실측 보강: 감가상각 관련 659행 중 **CF(현금흐름표) 308행 · BS 249행 · CIS 102행**.
BS의 249행은 `감가상각누계액`으로 **비용이 아니라 스톡**이다 — 잘못 매칭하면 조용히
틀린다.

### (b) 우리 적재 로직의 결함 — 코드로 고친다
`cf_operating`/`cf_investing`/`cf_financing`이 전체 63%인데, 기간별로 보면:

```
A 98.9% · Q1 99.1% · Q2 99.0% · Q3 99.2%
Q4  0.0% · TTM 0.0%     ← 여기가 전부를 끌어내린다
```

손익은 "연간 − 앞 3분기"로 Q4를 만드는데 **현금흐름은 같은 처리를 안 한다.**
LLM 불필요, 적재 함수 수정으로 해결된다.

### (c) 계정명 변형 — 여기가 LLM이 실제로 유용한 곳
표준코드 커버리지 실측 **76.9%**, 센티널(`-표준계정코드 미사용-`) **23.1%**.
센티널 행은 계정명으로 맞춰야 하는데 변형이 심하다:

```
확정급여제도의 재측정요소        520건
순확정급여부채(자산) 재측정요소    178건
순확정급요부채의 재측정요소       128건
순확정급여부채 재측정요소          59건
확정급여제도의재측정요소           24건   ← 띄어쓰기만 다름
```

`account_concepts.name_alts`가 이걸 흡수하는 장치인데, 별칭을 손으로 채우는 건 한계가 있다.

**LLM 적용 규칙 (반드시 지킬 것):**
- LLM은 **분류만** 한다 — "이 계정명이 어느 concept인가". 숫자를 생성하지 않는다.
- 산출물은 `account_concepts.name_alts`에 들어가는 **매핑**이지 금액이 아니다.
- 매핑에는 **근거와 신뢰도**를 남기고, 사람이 검수할 수 있어야 한다.
- 금액은 언제나 DART 원본에서 온다. 매핑이 바뀌면 재계산으로 반영한다
  (재계산 결정성은 134,279행 전수로 검증됨).

## 3. 자주 쓰이는 계산값을 미리 넣는다

### 결정
화면에서 반복해서 쓰이는 파생 계산은 컬럼으로 저장한다. 현재 `gpm_pct`·`opm_pct`·
`npm_pct`·`roe_pct`·`debt_ratio_pct` 5개가 그것이고, 앞으로 계속 추가된다.

### 추가 기준
아무거나 넣으면 컬럼이 무한정 늘어난다. 다음을 만족할 때만 넣는다.

1. **회사를 가로질러 정렬·필터하는가** — 스크리너에서 쓰는가. 아니면 화면에서 계산해도 된다.
2. **입력 컬럼이 이미 있는가** — 없으면 1번(컬럼 추가)이 선행이다.
3. **정의가 하나로 확정됐는가** — `net_debt` 같은 사례를 반복하지 않는다.

### 안전장치
`internal.fin_periods_refresh()`가 계산 규칙의 **단일 정의**다. 사본을 만들지 않는다.
컬럼 추가는 이 함수만 고치고 재계산하면 되고, **재계산이 결정적임이 전수 검증**돼 있다
(3,978개사·134,279행, 6개 period_type 지문 전부 동일).

## 4. Phase 3 주석 항목 — 컬럼 vs long 테이블

### 대상
| 항목 | 원천 |
|---|---|
| 판관비 세부 (급여·복리후생·광고선전) | 손익 주석 |
| R&D 지출 (총액·자산화·비용화·매출대비) | `연구개발활동` |
| 부문별 매출 | 영업부문 주석 |
| 감가상각비 (2-(a)에서 넘어온 것) | 유형자산 주석 |
| 최근 연혁 | `I. 회사의 개요 → 2. 회사의 연혁` |

**재무제표 본표에는 없다.** 삼성전자 2024 연결 손익계산서는 17행이 전부이고
`판매비와관리비`는 81.6조 **한 줄**이다.

### 논의 필요 — 잠정 방향
**long 테이블을 권한다.** 근거:

- 세부 항목은 회사마다 다르다. 컬럼으로 펴면 1번과 같은 롱테일 문제가 규모만 키워
  재발한다.
- 세부 항목은 대개 **한 회사 상세 화면**에서 쓰인다. 회사를 가로지르는 질의가 아니므로
  컬럼일 필요가 없다.
- 예외: "R&D/매출 비율"처럼 **가로지르는 것이 명백한 소수**는 컬럼으로 승격한다.

제안 형태:
```
(corp_code, period_key, fs_div, concept, item_name, amount, source_rcept_no, extracted_by)
```
`extracted_by`로 규칙 기반 추출과 LLM 추출을 구분한다.

### LLM 적용
주석은 비정형 텍스트이므로 **여기가 LLM의 본령**이다. 2-(c)와 달리 분류가 아니라
**구조화 추출**이다.

지켜야 할 것:
- 추출 결과에 **출처(rcept_no·섹션)를 반드시 남긴다.** 원문 대조가 가능해야 한다.
- **자릿수 sanity check**를 건다. (전례: 에코프로머티 2026 Q1을 8,220억으로 넘겼으나
  DART 원문은 1,665억. FY2025 연매출 3,925억인데 한 분기가 두 배라는 산술 모순으로
  걸렀어야 했다.)
- 원문 ZIP은 Storage에 남아 있으므로 **재추출이 언제든 가능**하다. 추출 규칙이 바뀌면
  DART 재호출 없이 다시 뽑는다.

## 실행 순서

1. **[코드]** Q4·TTM 현금흐름 파생 — 결함 수정, LLM 불필요
2. **[정의]** `net_debt` 기준 확정 + `debt_ratio_pct` 정밀도 결정
3. **[스키마]** 6개 컬럼 추가 (유동자산·유동부채·당좌자산·자본금·유보액·이자비용)
4. **[Phase 3]** 전 종목 원문 Storage 적재 (삼성 시험 중)
5. **[설계]** long 테이블 스키마 확정
6. **[LLM]** 계정명 별칭 매핑 → `account_concepts.name_alts`
7. **[LLM]** 주석 구조화 추출 → long 테이블

1~3은 Phase 3와 독립이라 지금 할 수 있다.
