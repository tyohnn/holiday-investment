# 주석 블록 확장 설계 — 5블록 → 계정 단위 추출

2026-08-25. 삼성 2025 사업보고서(20260310002820) 주석 실측 기반.

## 실측 — 주석은 어떤 모양인가

```
연결재무제표 주석  163,372자   (+ 별도 주석까지 2개 섹션 330,437자)
```

**소제목이 마크다운 헤딩이 아니다.** `가. 연결회사의 개요`·`나. 종속기업 현황` 같은
구분이 본문 텍스트에 인라인으로 뭉쳐 있고, 표만 마크다운 표로 살아남았다. 즉 섹션
분할(`split_sections`)은 주석을 **한 덩어리**로 준다 — 그 안에서 표를 찾는 건 별도 문제다.

표 자체는 깨끗하다. 실측 예(감가상각비 기능별 배분):

```
| 감가상각비의 기능별 배분 | — |
| 당기 | (단위 : 백만원) |
| — | 매출원가 | 판매비와관리비 등 | 기능별 항목 합계 |
| 감가상각비, 유형자산 | 38,101,542 | 5,504,198 | 43,605,740 |
```

패턴이 보인다: **캡션 → 기간(당기/전기) + 단위 → 헤더 → 값**. 그리고 당기·전기가
**같은 표가 아니라 나란한 두 표**로 나온다.

- **감가상각비** — `fin_periods.depreciation` 이 19.3% 밖에 안 채워진 것(EBITDA)

## 핵심 설계 판단 — `fin_details` 가 아니라 `financial_facts` 쪽이다

### 두 종류를 구분해야 한다

주석에서 나오는 것은 성격이 갈린다:

**(가) 계정 값** — 본표 계정의 세분 또는 본표에 없는 계정
예: 판관비 세부(급여·복리후생·광고선전), 이자비용, 감가상각비, 법인세 세부
→ **`financial_facts` 와 같은 축**이다: `(corp, year, reprt, fs_div, sj_div, account, amount)`
→ `fin_periods` 가 이걸 읽어 컬럼을 채울 수 있다 (이자비용·감가상각 결손 해소)

**(나) 계정이 아닌 사실** — 축이 계정이 아닌 것
예: 부문별 매출(축=부문), 종속기업 목록(축=법인), 특수관계자 거래(축=상대방),
우발부채(축=사건), 시장점유율(축=제품)
→ **`fin_details` 가 맞다**: `(corp, period, concept, item_name, amount)`

지금 5블록은 우연히 전부 (나)였다. 확장하면 (가)가 대량으로 들어온다.

### 왜 (가)를 `fin_details` 에 넣으면 안 되나

1. **`fin_periods` 가 못 읽는다.** `internal.fin_periods_rebuild()` 는 `financial_facts`
   를 읽는다. 이자비용을 `fin_details` 에 넣으면 이자보상배율 컬럼을 만들 수 없다 —
   추출의 가장 큰 실익이 사라진다.
2. **계정 개념 사전이 이미 있다.** `account_concepts` 가 `account_id → concept →
   name_alts` 매핑을 들고 있다. (가)는 그 사전을 그대로 쓸 수 있는데
   `fin_details.concept` 은 별도 어휘라 두 벌이 된다.
3. **정정 추적.** `financial_facts` 는 `rcept_no` 로 정정 체인을 따라간다. 계정 값은
   정정 대상이다.

## 제안 구조

```
주석 원문 (Storage)
   ├─ (가) 계정 값 → financial_facts   [sj_div='NOTE' 신설]
   │        └→ fin_periods 가 읽어 이자비용·감가상각 컬럼 채움
   └─ (나) 계정 아닌 사실 → fin_details / corp_history  (현행 유지)
```

### (가)를 위한 스키마 판단

`financial_facts` 에 그대로 넣되 **출처를 구분**해야 한다. 현재 스키마에
`sj_div` 가 `BS|IS|CIS|CF|SCE` 인데 주석은 그중 어디도 아니다.

선택지:
- **A. `sj_div='NOTE'` 추가** — 기존 축을 그대로 쓰고 값 하나만 늘린다. `fin_periods`
  개념 테이블이 `sj_div` 로 판정하지 않으므로(계정 개념 테이블 기반) 충돌이 적다.
- B. 별도 테이블 `note_facts` — 격리는 되지만 `fin_periods` 가 두 곳을 읽어야 한다
- C. `financial_facts` 에 `source` 컬럼 추가 — A 와 비슷하나 스키마 변경이 더 크다

**A 를 권한다.** 다만 확인이 필요하다:
- `financial_facts` 에 `sj_div` CHECK 제약이 있는지
- `extracted_by` 에 해당하는 컬럼이 없다 — 규칙/에이전트 산출물 구분을 어떻게 할지
  (`account_id` 에 센티널을 쓰거나, 컬럼을 추가하거나)

## 파싱 난점 (실측)

1. **주석이 한 덩어리다.** 163,372자에서 원하는 표를 찾아야 한다. 캡션 키워드로
   윈도우를 자르는 방식(현행 `cut_keyword_windows`)이 그대로 쓰인다.
2. **당기/전기가 나란한 두 표다.** 한 표에 두 기간이 아니라, `당기` 표와 `전기` 표가
   따로 나온다 — 기간 라벨을 표 캡션에서 얻어야 한다. 현행 `parse_period_col`(헤더
   기반)과 다른 경로가 필요하다.
3. **단위가 캡션에 있다.** `(단위 : 백만원)` — 헤더가 아니라 캡션 행이다.
4. **다단 헤더.** 무형자산 표처럼 3단 헤더 + 병합 붕괴가 있다.

1·2·3 은 규칙으로 가능해 보인다(패턴이 반복적). 4 는 LLM 영역.

## 실행 순서 제안

1. **선행**: 분기 `period_key` 수정 (진행 중) — 주석도 분기마다 나오므로 이게 먼저다
2. `financial_facts` 에 `sj_div='NOTE'` 수용 여부 확인 (CHECK 제약·`fin_periods`
   rebuild 영향)
3. **(가) 3종 파일럿**: 판관비 세부·감가상각비·이자비용을 삼성 1개 보고서에서 추출 →
   `financial_facts` 적재 → `fin_periods` refresh → 이자보상배율·EBITDA 가 실제로
   채워지는지 확인. **이게 이 확장의 가치를 증명하는 지점이다.**
4. (나) 확장: 특수관계자·우발부채 (교재 우선순위)
5. 나머지
