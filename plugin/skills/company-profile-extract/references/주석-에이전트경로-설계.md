# 주석 계정 추출 — 에이전트 경로 설계 (2026-08-26)

감독 재지시("개념은 닫고, 라벨만 연다")에 따라 설계·구현·5개사 실측·삼성 회귀를 완료했다.
파일: `scripts/extract_notes_full.py`(A, 확장), `scripts/notes_agent.py`(B/C, 신규),
`references/주석-라벨별칭.json`(로컬 별칭 축적 파일, 신규 — DB `account_concepts`는 안 건드림).

## A. account_detail 배선 — 완료 + 부수적으로 발견한 실버그 수정

`build_facts()`가 그룹별 출처 캡션(9종: 비용의 성격별 분류 공시 / 판매비와관리비에 대한
공시 / 금융수익 및 금융비용(수익·비용) / 기타수익 및 기타비용(수익·비용) / 지분법평가내역
/ 영업활동현금흐름(조정내역·운전자본변동))을 facts 튜플에 실어 `fact_row()`까지 배선했다.
`account_detail = 'NOTE:<캡션>'`. CF 조정/운전자본처럼 같은 값이 우연히 같아도(예:
유형자산처분손실 57,404/124,018이 기타비용표·CF조정표 양쪽에 동일값으로 등장) 캡션이 달라
natural_key가 갈리므로 더 이상 dedup으로 접지 않고 두 출처를 각각 보존한다(49→52행 중 +1).

**부수 발견·수정**: `_parse_financial_income_cost()`가 '외환차이' 라벨을 수익측/비용측
구분 없이 저장해, `add("외환차이(금융수익)", ...)"/add("외환차이(금융비용)", ...)` 가
**리터럴 불일치로 늘 빈 조회**였다(`_parse_other_income_cost`의 '기타'는 이미 섹션별
재라벨링 처리가 있었는데 이 함수만 빠져 있었다). git HEAD(이 세션 시작 시점)에도 이미 있던
결함이고, DB의 기존 49행에도 이 두 개념(외환거래이익/외환거래손실, 당기 102,323/102,160억)
이 **처음부터 없었다** — 채점표 문서의 '일치' 판정은 수동 계산 기준이었던 것으로 보인다.
`_parse_other_income_cost`와 동일한 섹션별 재라벨링 패턴으로 수정 → 39종 재현시험에서
"성격별비용" 재사용 안전성 논증과 같은 방식으로 both-pass 확인 후 실제 반영(52행 재적재,
아래 회귀 참고).

## B/C. "개념은 닫고, 라벨만 연다" — notes_agent.py

`CONCEPT_REGISTRY`는 52개 원문 세부 라벨(=`extract_notes_full.py`의 add() 호출부와 문자
그대로 일치, FnGuide 표시 기준 39버킷의 파생 원천)로 **닫혀 있다**. 파이프라인:

```
① 규칙(extract_notes_full.py, canonical_label + 로컬 별칭)이 먼저 훑는다
② 못 채운 개념만 notes_agent.py prepare → 원문 절단 + "이 개념을 뭐라 부르나?" 질문 파일
③ 에이전트가 원문 읽고 raw_label 확인 → ingest 가 원문 재검색으로 검증
④ 검증된 새 라벨을 references/주석-라벨별칭.json 에 즉시 누적
      → extract_notes_full.py 가 다음 실행부터 그 별칭도 규칙으로 찾는다
```

`account_nm`에는 항상 canonical_label(정본 개념명)을 저장한다 — 회사 원문 표기는
`account_detail = 'NOTE:AGENT:<source_table>(원문라벨=<raw_label>)'`에만 남긴다. 그래야
`fin_periods_rebuild()`의 개념 매칭(`account_concepts.name_alts` 기준)이 흔들리지 않는다.

**게이트(C, 그대로 유지)**: 그룹 세부합 vs 본표 총액 ±1%. 대조값은 ① `financial_facts`
본표(sj_div IN IS/CIS)에서 후보 account_nm(`GROUP_TARGET`, 6개 그룹만 — 판관비/금융수익/
금융비용/기타수익/기타비용/지분법)을 찾거나, ② 없으면(CF 조정/운전자본·비용의 성격별처럼
본표에 직접 대응 라인이 없음) 에이전트가 옮겨 적은 그룹 내부 소계(`group_subtotal`, DB에는
안 실림)로 대조한다. 실패하면 **그룹 전체를 보류**한다(부분 적재 없음).

**안전장치**: `verify_raw_label_in_text()`가 매 항목마다 그 회차의 주석 섹션 **전체**를
다시 읽어 raw_label이 실재하는지 확인한다 — 실패하면 적재도 별칭 등록도 하지 않는다.
`account_concepts`(DB, `internal.fin_periods_rebuild()` 의 실제 입력)에는 절대 쓰지 않는다
— `propose-db-aliases` 서브커맨드가 dry-run 으로만 후보를 보고한다(실제로 실행해 확인함,
아래 참고).

### 개념 자체가 없는 것(정상 부재, 별칭으로 못 고치는 것)

- LG(지주): 판관비 세부공시 표 자체가 이 절단 범위에 없음(지주사 특성 — 소수 임직원,
  단순 비용구조 추정). "비용의 성격별 분류"는 있으나 재고자산변동×기능(판관비/매출원가)
  매트릭스라 우리 registry의 "감가상각비/무형자산상각비 단일 값"과 구조가 다르다.
- 삼성화재(보험): 판관비·성격별비용 캡션 자체가 없다 — 보험업 IFRS17 손익 표시가 제조업과
  본질적으로 다르다(예정사업비 등 보험 고유 개념). 반면 "이자비용(금융원가)"는 리터럴로
  **정확히 일치**했다(라벨은 같고 표 구조만 다름 — 매칭 실패 원인이 항상 라벨 변이는
  아니라는 증거).
- GS건설(건설): 판매촉진비/운반비/서비스비/경상연구개발비 자체가 없다. 대신
  대손상각비·기술개발비·하자보수비 같은 건설업 고유 계정이 있다 — 39종 registry 밖의
  **새 개념**이라(감독 지시: "새 개념을 찾아내는 게 아니다") 이번 세션 범위에서 다루지
  않았다.
- 금호석유화학: 그룹 게이트가 **정직하게 실패**한 사례(중요 검증) — SGA는 23개 원문
  세부항목인데 registry는 9개만 추적해 세부합(241,036백만)이 본표 판관비(332,101백만)의
  73%에 그쳤다(차이 27.4% ≫ 1%) → sga 그룹 전체 보류. 기타수익/기타비용도 유사(세분화가
  너무 잘 돼 있어 Samsung의 "기타" 잔여개념과 범위가 다름, 차이 95%+). **부분 오적재를
  막는 게이트가 의도대로 작동했다** — registry가 그 회사의 실제 세분화 수준을 못 따라가면
  적재를 거부하는 것이 맞는 동작이다.

### 실제 적재 검증 (end-to-end 1건)

금호석유화학의 `equity_method_pnl`(지분법손익)은 게이트를 실제로 통과(당기 차이 0.0000%,
전기 0.0009%)해 `--load`로 실제 적재까지 완료했다:
`financial_facts` corp=00106368 rcept=20260318001268: account_nm='지분법손익',
amount=131,053백만, account_detail='NOTE:AGENT:9-2. 당기 및 전기 중 공동기업 및
관계기업투자의 증감내역(합 계 행)(원문라벨=지분법손익)' — prepare→에이전트 판독→원문
재검증→게이트→적재 전 구간이 새 회사에서 실제로 동작함을 확인했다.
